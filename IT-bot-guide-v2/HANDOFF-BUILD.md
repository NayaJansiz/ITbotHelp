## Design (measured on 8 subjects with confirmed lecture folders, ~200 solved questions as ground-truth proxy)
- A subject's lectures are 365K–873K characters (roughly 120K–290K tokens, rough estimate): too big to send whole. Keyword search over ~1400-character passages finds the supporting passage only 56–73% of the time (top 3–8) and 82% at top 12 → rejected (silent misses).
- Routing each question to a **whole lecture file** (keyword ranking): right file in top-1 72%, top-2 84%, **top-3 91%**. So each question is put into the packs of its top-3 lecture files (questions are short; duplicates are cheap).
- Per lecture the pack = fixed instructions + the lecture file + its questions (+ list of images to attach). Claude replies with JSON lines: `{"id","a","src":"LECTURE|NOT-FOUND","ref","q":<verbatim quote>,"e":<explanation ≤150 chars>}`.
- **Machine checks (0 tokens)** in `merge_answers.py`: the quote must exist word-for-word in that lecture (letters/digits skeleton, so markdown/spacing don't matter), letter inside options, explanation ≤200 chars with the lecture marker `(م#)` appended (the 2026-10-17 bot update had removed these markers (466 visible explanations had one before, 1 has one now) — they are restored for every LECTURE-verified answer), no overwrite of an existing different answer (reported as CONFLICT-EXISTING), conflicts between packs reported, missing replies reported.
- Leftovers (NOT-FOUND in all packs) → `INFERRED.md` pack → answers tagged `(استنتاج)` and `needs_review=1`.
- Provenance (src, file, ref, quote, date) is written to `data/provenance/subject-<id>.json` (the database itself has no readable source field: `answer_source` is just 0/1).
- Images: 90 visible questions have one (year 1: 52, year 2: 3, year 3: 35). A question with an image is only made visible if the image file exists under `media/`.

### Part 2A — Sources from student PDFs (cheapest-token design)
Principle: **a PDF is converted to text ONCE, on the student's computer, with 0 tokens; Claude only ever sees small text packs, and only for questions that machine checks could not settle.** Claude chats have no memory and there is no API key, so "not re-uploading" means: the converted text lives in the repo/site, and the pack builder re-creates a small pack on demand. (Claude.ai Projects could also hold files across chats, but how it counts tokens/limits is untested here: treat as optional, not as the design.)

1. **Ingest once** — new `tools/ingest_pdf.py <pdf> --subject N --name "<lecture name>"`. Python, runs locally. Uses PyMuPDF (new dependency, accepted by the owner; the existing tools stay no-package). Output: `sources/<subject-id>/<slug>.md` with a page marker before every page (`<!-- p12 -->`), plus an entry in `sources/manifest.json`: `{sha256 of the PDF, pages, chars, per-page sha256, ingested date, version}`. The text, the page images of figures (item 3) and the manifest are committed to the public repo (owner: no privacy concern). The PDF itself is NOT committed (size); its sha256 is kept so the same PDF is recognised again.
2. **Clean (measured on the real sample `WP-lecture_3.pdf`, 48 pages, 3.1 MB)**: the whole lecture text is 20,260 characters, roughly 5,000 tokens (estimate: characters/4; not a real tokenizer count). Dropping bare page numbers saves only 1.6%. Dropping lines repeated on 3+ pages saves 13% but would delete real code lines (`<style>`, `color: red;`, `</body>`), so it is REJECTED. The earlier "10–30% fewer tokens" estimate was wrong and is withdrawn: cleaning is limited to bare page numbers and blank lines. Quote matching already ignores spacing/markdown (`flat()`), so this cannot break verification. **Consequence: text is cheap, page images are expensive** (a page rendered at 110 dpi is about 1,200 tokens by the w*h/750 estimate, i.e. one image costs about a quarter of this whole lecture's text), so the design is: send the whole lecture text, attach images only when needed.
3. **Code and diagrams (the PDFs are mostly text + code + diagrams)**:
   - **Code blocks come in two kinds (owner, rev. 3)**: (a) real text -> in the sample PDF this is the normal case (HTML/CSS code on pages 16-18, 29, 34-39, 41-46 extracts as text); (b) pasted as an image -> cannot be quoted or searched. Measured on the sample: only 2 of 48 pages (6 and 48, 4%) hold information that exists only inside a picture. Page 6 is the CSS-modules diagram (its labels are only in the image); page 48 is the contextual-selectors code with annotations (the text layer has just the title, 34 characters). Detection that separated exactly these two pages: one image covering 25% or more of the page AND under 200 characters of text. Pages 21-22 (screenshot of a browser result with the code already in the text layer) are correctly NOT flagged. Handling of (b): treated as a FIGURE page (image attached only when routed to it, answer tagged `FIGURE`, `needs_review=1`). Optional OCR (tesseract) only for routing, never as proof for a quote. One PDF is a small sample: the thresholds are re-measured on the next PDFs.
   - **Code as text**: extract with line breaks kept. NO code fencing and NO font-based code detection: measured, it fails (only 9 pages show a monospace font, while code on pages 16-18 uses a proportional font), and quote matching ignores spacing anyway. Indentation is lost in the text layer of this PDF (all code lines start at the left edge): harmless for HTML/CSS, but would matter for Python-style courses; check on the first such PDF. Reading order of diagram labels is scrambled in extraction (e.g. slides 8-11 give `selector { property: value; ... } declaration block declaration`): a quote spanning diagram labels may fail the machine check and fall to NOT-FOUND, which is the safe failure.
   - **Diagrams / figure pages**: a flagged page (rule above) is exported once as `sources/<id>/figs/<slug>-p<N>.jpg` at about 110 dpi (measured 73-87 KB per page, 1100x825 px) and marked `<!-- fig: figs/<slug>-p<N>.jpg -->` in the text at that page. The page's text (title, captions) stays in the pack.
   - **Figure images cost tokens, so**: a pack attaches a figure page only when one of its questions is routed to that page (keyword overlap with the page text/caption) or the question is already tagged as needing a picture. For a lecture this small (about 5,000 tokens of text) no page-level routing is needed: the whole lecture goes in; only the figure images are conditional.
   - **A quote cannot be machine-verified against a picture**. Answers that depend on a diagram are tagged `src: FIGURE` with page reference, are NOT auto-verified, and are marked `needs_review=1` until a human confirms (honest label instead of fake verification).
   - **Scans** (no text layer at all): listed in `sources/<id>/<slug>.pages.json` as `needs-OCR`, never silently skipped; OCR is a later add-on (decide after seeing how many pages are affected).
4. **Update when the PDF changes** — re-run ingest on the new PDF. Same sha256 -> nothing happens. Different sha256 -> per-page hashes show which pages changed; only those pages are rewritten.
5. **Re-verify for free first** — every solved answer already has provenance (file, ref, verbatim quote). After an update `tools/reverify.py` re-checks each stored quote against the new text (0 tokens). Quote still found -> answer stays verified. Quote missing -> that question only is marked `stale` and goes into the next pack. So an updated PDF costs tokens only for the questions it actually affected.
6. **Packs stay as designed** (route each question to its top-3 source files; measured 91% for lecture files). A PDF is split into source files by chapter/lecture if it has bookmarks, otherwise by fixed page ranges. Page-level routing is NOT adopted: passage-level search measured 56–73% (silent misses). Only already-unsolved or `stale` questions are packed (existing `--all` stays available for a full audit).
7. **Config**: `config/subjects.json` gets `"sources": [...]` per subject (repo lectures and/or `sources/` files). This removes the old limit "only 8 subjects have a lecture folder": any subject with an ingested PDF now gets a real LECTURE pack instead of only the INFERRED pack (Part 6 changes accordingly).
8. **Public repo**: decided by the owner: lecture text and figure images go in the public repo. (The owner's decision, not a legal check; if a university or author objects, `sources/` can be removed without touching answers, since provenance only keeps short quotes.)

### Part 2B — Question intake from Telegram polls (updates and pictures)
Facts from the current data: 95 questions have an image, only 51 distinct image files; **14 images are shared by 58 questions** (e.g. `y1_photo_2…jpg` serves `y1:p49`–`p52`). So many-questions-to-one-picture is the normal case, and the schema has a single `image` TEXT per question. A Telegram poll cannot carry a picture: the picture is a separate message near the poll, which is where pictures get lost or mismatched.

1. **Intake tool** — new `tools/ingest_polls.py <telegram-export-folder> --year Y --subject N`. **Measured on the real sample (`messages.html`): the export is Telegram Desktop's HTML format, NOT JSON, so the parser reads HTML**: each message is `div.message` with `id="message<N>"`; a poll is `div.media_poll` with `div.question` and one `div.answer` per option; a photo is `a.photo_wrap` whose `href` is the full file and whose `<img>` is only a `_thumb.jpg`; a photo caption is in `div.text`; forwarded messages carry the original sender and original timestamp. The sample has 31 polls, 3 photos, 1 caption. Facts about the data: (a) answers in the HTML are shown with a `- ` prefix that must be removed once (the question is `1- ...`, `2_ ...`, `24ـ ...`: numbering with different separators, to be stripped from the question text); (b) options keep tatweel characters (`ـ10`), which the existing DB also keeps, so normalisation must drop tatweel on both sides; (c) polls show `Anonymous poll` and a vote total only: **no correct answer is exported**, so every answer comes from the sources workflow; (d) photo file names contain the EXPORT time (`photo_2@19-10-2026_14-28-31.jpg`), not the original time, so they change at every export. **Rev. 5: the full export (HTML + photos folder) was received and is identical in `messages.html` to the first upload.** Photos checked: `photo_1` is the group's icon from a service message (`changed group photo`), NOT a question picture: only photos inside `div.message.default` are considered, and `_thumb.jpg` files are ignored. `photo_2` (1280x636, 151 KB) is a hand-drawn circuit (Thevenin: R1=3, R2=R3=8, R4=2, E=12 V, I=8 A, load RL), matching polls 6-9. `photo_4` (719x926, 94 KB) is a hand-written sheet with the circuit AND the five problem statements (equivalent conductance, current in R2, total current, equivalent resistance, power in R2), matching polls 24-28 exactly: the poll text alone is unanswerable without it. `photo_3` (1184x1115, 166 KB) was not viewed. Image cost estimate (w*h/750): about 1,100 / 1,800 / 900 tokens for photos 2 / 3 / 4. Consequence: these are hand-drawn/handwritten (OCR is not an option), and answers to such questions are computed from the picture, not quoted from a lecture, so they are tagged `FIGURE`, cannot be machine-verified, and rely on the student's review (Part 2D) and the approvers. Still unverified: whether the database's existing `media/` files have identical bytes to these photos (those media files are not in the guide zip, so no hash comparison was possible); the rule "an existing picture is kept" covers a mismatch.
2. **Identity (so updates replace, not duplicate) — rule changed after measurement**: **message ids cannot be the identity.** The sample's polls are forwarded copies: their ids (`460281`...) belong to the student's own group and do not equal the database keys of the same questions (`y1:p43`...), and another student forwarding the same polls into another group would get other ids (or even the same number for a different question). So: (1) identity = **fingerprint** = normalised question (numbering and tatweel removed) + options (export `- ` prefix and tatweel removed, order-independent); (2) key is used only as a hint for rows that already exist. **Tested: all 31 sample polls matched an existing database row by fingerprint (31/31, no duplicates among the 31, no two polls with the same text and different options).** New questions with no match get a new key `f:<first 12 chars of the fingerprint hash>` (not tested: whether `bot.py`/`bot_db_tool.py` accept keys other than `y{N}:p{N}`; verify before building). Forwarded metadata (original sender + original timestamp) is stored as a batch label; in the sample all 31 polls share the same sender and the same second, so the batch is recognisable. A fingerprint seen again under a different key is recorded in `data/aliases.json`.
3. **Update policy per existing question**: identical -> skip. Question text changed -> update text. Options changed -> update options and **re-map `correct_index` by option TEXT, not position**; if the correct option's text no longer exists, keep the row but set `needs_review=1` and hide it until re-solved. A stored verified answer is never overwritten by intake (existing CONFLICT-EXISTING rule). A question missing from a new export is NOT deleted (exports may be partial); it is only listed in the report.
4. **Pictures — never lose one**:
   - Store each picture once by content: `media/<sha256-first-12>.<ext>`, with `data/media.json` = `{id: {file, sha256, original names, used_by:[keys]}}`. The same photo exported again under another name (`photo_9` vs `photo_3`) has the same hash, so it is reused, not duplicated and not broken.
   - Questions reference **media ids** (list), not export filenames. One id may be used by any number of questions; one question may have more than one id.
   - **Students do NOT need to name pictures.** They send the export as it is (messages + photos folder); the tool binds by the rule below. If it cannot decide, the student gets a short review list with the picture next to the polls and answers a one-line choice (e.g. `photo_9 -> p168,p169`). Optional shortcut, only if they want certainty: write the question numbers in the photo caption (e.g. `Q3-5`); the tool reads it first. Not required.
   - **Binding rule — the first version was WRONG, measured**: "a photo applies to the polls that follow it until the next photo" over-binds. In the sample the existing database (used as ground truth) binds `photo_2` to 4 polls (`y1:p49-p52`, numbers 6-9), `photo_3` to 2 (`p66-p67`, numbers 22-23) and `photo_4` to 5 (`p69-p73`, numbers 24-28). The simple rule would attach `photo_2` to 16 polls (6-21, mostly true/false theory), `photo_4` to 8 (24-31): 26 candidate bindings, 11 correct, 15 wrong (58%). The sample's own cue: question text for picture-based polls is numeric (values of a circuit) while the theory polls are true/false, but that is language-specific and not a rule to trust. **New rule**: (1) a photo's candidate run = the polls after it up to the next photo (or up to a cap); (2) existing rows that already have a picture keep it, intake never replaces it; (3) for rows without a picture, the candidate is only PROPOSED: Claude's reply for that question carries `uses_image: true/false` (the picture is attached to that pack anyway, since numeric questions need it to be solved), and (4) the student confirms or removes each binding on the review screen (Part 2D) with the picture shown next to the question; (5) nothing is bound silently when the answer to (3) is missing. The photo caption (`النموذج C`) is stored with the media and shown in the review screen.
   - **Update safety**: re-ingest merges images (union); it never sets a picture to empty. Removing a question never deletes its media file (only an orphan report). A question that had a picture and now has none is a hard ERROR in `check_bot.py --strict` and `--compare`. A visible question whose media file or hash is missing stays hidden (extends the existing rule).
   - **Bot compatibility**: `bot.py` reads one `image` path. Build step writes `image` = the single file; if a question has 2+ pictures the build stitches them into one image (needs Pillow, new dependency). The cleaner alternative, `bot.py` sending several photos before the poll, needs the bot owner and is not assumed.
   - Pack side: `make_packs.py` already lists each pack's images by name; change it to media ids and attach each shared picture once per pack.
5. **Report** after every intake (also posted on the PR in Part 3): added / updated / unchanged / alias-matched / hidden-for-review / images bound / images needing review / questions absent from the export.

### Part 2C — Several students at once (same or different subjects)
Problem: Part 1 keeps one `data/questions/subject-N.json` per subject. Two students sending changes to the same subject would edit the same file and Git would report merge conflicts. Design: **students never edit `data/` directly.**
1. **A student's pull request only ADDS new files with unique names**: `intake/<subject>/<date>-<sha8>.json` (polls), `replies/<subject>/<pack>-<sha8>.jsonl` (answers), `sources/<subject>/<slug>.md` + figures (text), `media/<sha12>.<ext>` (pictures). Names contain a content hash, so two students can never overwrite each other and an identical file sent twice is the same file.
2. **One GitHub Action is the only writer of `data/`.** It applies the pending files one at a time (`concurrency` group, so never in parallel) with the same machine checks as `merge_answers.py` and the intake rules of Part 2B, then runs `bot_db_tool.py verify` and `check_bot.py --strict`. The order of applying is the order of merging.
3. **Same question from two students**: same key or fingerprint -> the second one is "unchanged" or "update", never a duplicate. **Same picture**: same hash -> same file.
4. **Same answer twice, different answers**: identical -> merged once. Different verified answers for the same question -> existing CONFLICT-EXISTING report, nothing overwritten, flagged for review.
5. **Same lecture, two different PDF versions** (e.g. two students with an old and a new copy): never overwritten silently. The second is stored as a candidate `<slug>@<sha8>` with a page-diff report; the maintainer picks which is current (one decision). Questions verified against the old text are re-verified by the free quote check (Part 2A item 5).
6. **Approval (owner, rev. 3)**: the owner and one teammate are collaborators and approve/merge student pull requests manually. Students work through GitHub (fork -> pull request, as the page already links). So: (a) the Action's report is posted on each PR as the approval checklist (what is added/updated/conflicting, images needing review); (b) a PR with any ERROR or unresolved image-review or conflict is not merged until fixed; (c) with only two approvers, PRs that touch the same subject are merged one at a time (the single-writer Action already serialises the data change); (d) branch protection on `main` requiring the checks to pass and one review is recommended; whether to turn it on is the owner's repository decision, and the page's guard remains advisory until then. Auto-merge is NOT part of the plan.

### Part 2D — Student review and editing BEFORE submitting (new owner requirement)
The student must be able to edit the answer or the explanation when reviewing Claude's results, before the pull request is created. The site already has the paste-reply step (`#reply` textarea in `site/index.html`); a **review screen** is added between "reply validated" and "submit".
1. **Per-question card**: question and options (read-only; changing them would change the identity), picture(s) with a "this picture belongs to this question" switch (Part 2B binding), the chosen answer as a selector over the options, the explanation in an editable box with a live counter (limit 200 characters including the `(م#)` marker, the bot's limit), the source line and verbatim quote (read-only), and a status badge: VERIFIED / FIGURE / NOT-FOUND / CONFLICT-EXISTING / EDITED. Filter by status, and one button to accept all VERIFIED cards untouched, so the student looks first at what is not VERIFIED.
2. **Explanation edits**: always allowed; they cannot break verification (the explanation is not proof). Limit enforced live and again by the Action (`merge_answers.py` check). Marked `e_edited: true` in the file so approvers can see it.
3. **Answer edits**: allowed. The machine answer is kept as `a0`/`src0`, the new one is recorded with `src: STUDENT` and the old quote is cleared (it no longer supports the new answer). If the student pastes a supporting quote, the check against the source text runs (in the page, using the public `sources/` text, and again in the Action): found -> the record becomes `LECTURE` verified (a human picked the answer, the lecture proves it); not found -> stays `STUDENT` and `needs_review=1`.
4. **Visibility of STUDENT answers — decided by the owner (rev. 5)**: students make their edits and open the pull request; the owners approve or refuse it. **Approval = merge.** A merged student answer is visible in the bot (stored with `src: STUDENT`, `needs_review=0`, kept in the history for audit); a refused pull request changes nothing; the owners can also request changes on the PR. No separate hidden state and no second confirmation step.
5. **Existing verified answers are never overwritten by a student edit.** If a student's edit disagrees with a stored LECTURE-verified answer, it appears as CONFLICT-EXISTING for the approvers (existing rule), not as a change.
6. **Nothing is lost if the page is closed**: edits are kept in the browser (localStorage; fine on a normal website, unlike the chat artifacts) and are saved into the reply file when the student submits. The submitted file contains the final values plus `a0`, `src0` and the edit flags, so the history is visible in the pull request.
7. **Approvers' report (Part 2C item 6)** lists, first: every STUDENT answer (original vs new), every picture binding the student changed, and every edited explanation.
8. **Not planned**: editing the question text or options in the review screen (it would change the fingerprint and create a different question); a student-side "undo all" beyond reloading the machine answers.
9. **Downloadable summary of changes (owner's extra feature, rev. 5)**: a button on the review screen (and again after submitting) creates `summary-<subject>-<date>-<sha8>.md` in the browser, with no tokens and no server, plus a "copy as text" button so the student can paste it into a message to the owners. Contents, in this order: student name/GitHub username (a field the student fills), subject and pack names, counts (added / updated / unchanged / hidden for review), then each CHANGE: changed answers (question number and text, original answer -> new answer, the student's optional reason, the quote if one was pasted and whether it was found), edited explanations (before -> after), changed picture bindings (picture name + caption + question numbers), then the items still needing a human (FIGURE, NOT-FOUND, CONFLICT-EXISTING). `sha8` is the same short hash as in the reply file name, so the owners can match the summary to the pull request. The same summary is also committed in the PR as `replies/<subject>/<pack>-<sha8>.summary.md`, so it cannot be separated from the data. Each changed answer gets an optional "reason" box on its card (recommended, not required) so approvers can decide faster. Plain Markdown, right-to-left safe.
